# ADR-0005: Асинхронный импорт отчётов через объектное хранилище и RabbitMQ

## Контекст

gateway кладёт отчёт в очередь, а
`parser` разбирает его, когда освободится. Разбор файла долгий и не должен
держать HTTP-запрос мобильного клиента.

## Решение

- **RabbitMQ** — очередь задач `report.uploaded`: durable, default
  exchange, `prefetch=1`, сообщения `amqp.Persistent` (иначе задача
  терялась бы при рестарте брокера, несмотря на durable-очередь).
- **Объектное хранилище** (сначала MinIO, теперь SeaweedFS, см.
  [ADR-0009](0009-seaweedfs-instead-of-minio.md)) для файлов. Сам файл
  в сообщение **не кладётся**, потому что брокеры сообщений не рассчитаны
  на объёмные payload'ы. В очередь идёт только ссылка.
- `parser` передаёт операции в `portfolio` **через его API**, а не напрямую
  в БД: вся валидация сделок остаётся в одном месте.
- Ошибки: невалидная задача или ошибка разбора — `Nack(requeue=false)`;
  временные ошибки хранилища или `portfolio` — `Nack(requeue=true)`.
- Лимит загрузки `MAX_UPLOAD_BYTES` = 32 МиБ (защита от исчерпания памяти).
- Позже добавлены:
  - компенсация (удаление объекта, если публикация не удалась);
  - поле `broker` и диспетчер парсеров;

## Рассмотренные альтернативы

| Вариант | Итог |
|---|---|
| **RabbitMQ** | принято: нужна простая семантика «одна задача — один воркер» |
| Kafka | отклонена: это журнал событий с consumer group'ами и повторным чтением истории; операционная сложность (Zookeeper/KRaft, партиции) избыточна для масштаба проекта |
| Файл внутри сообщения | отклонено: брокеры не для больших payload'ов |
| Запись `parser` напрямую в БД `portfolio` | отклонено: валидация должна быть в одном месте |

## Последствия

**Положительные:** клиент не ждёт разбора; новый брокер не затрагивает
`gateway`; повторная доставка безопасна (см. [ADR-0007](0007-idempotent-import-external-id.md)).

**Отрицательные и риски:** 
у RabbitMQ нет volume в compose, поэтому persistent-сообщения переживают
рестарт контейнера, но не его пересоздание; файлы с персональными данными
хранятся бессрочно.
