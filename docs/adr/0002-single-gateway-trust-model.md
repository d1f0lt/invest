# ADR-0002: Единственная точка входа gateway и доверие к `x-user-id` внутри сети

## Текущее состояние

- Проверка JWT удалена из `users`, `portfolio` и `parser`. `users` только
  **выдаёт** токены (`IssueToken`).
- У всех сервисов из `backend/services/*` убраны опубликованные порты.
  Порты инфраструктуры (postgres, S3, RabbitMQ) оставлены. 
- Реализован `gateway` — единственный сервис с открытым портом:
  - проверяет JWT `internal/auth.VerifyToken`: HS256 с
    `jwt.WithValidMethods(["HS256"])`, это защита от атак `alg: none`
    и algorithm confusion;
  - публичны только регистрация и вход (позже — `refresh` и `logout`),
    «третьего не дано», остальное — `401`;
  - после проверки сам выставляет id пользователя в исходящих вызовах:
    `x-user-id`.
- Внутренние сервисы доверяют `x-user-id` без криптографической проверки.

## Рассмотренные альтернативы

| Вариант | Итог |
|---|---|
| Проверка JWT в каждом сервисе (как было) | отказались: секрет размножен, логика дублируется |
| Сегментация docker-сетей | пока отложено |
| **Одна проверка в gateway + доверие внутри сети** | принято |

## Последствия

**Положительные:** `JWT_SECRET` знают только `users` и `gateway`;
`parser` не зависит от JWT; авторизация в одном месте.

**Отрицательные и риски:** любой контейнер внутри
compose-сети может выдать себя за любого пользователя, выставив нужный
`x-user-id` (см. [модель доверия](../05-security.md#53-авторизация-и-модель-доверия)).

**Что нужно сделать:** не добавлять в сеть посторонние контейнеры; при росте
системы вернуться к сегментации или mTLS.
